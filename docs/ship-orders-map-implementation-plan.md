# Планировщик корабельных заказов и движение на карте рынка

Дата: 23 сентября 2026 года. Обновлено: 24 сентября 2026 года.

Этапы A–B реализованы: единый предварительный расчёт 1–3 заказов, интерактивный выбор, сводка, карта и отправка через существующие команды. Сохранены текущие ограничения порядка портов. Формат хранения не изменён. Этапы C–E и оставшиеся удобства F ниже остаются предложением; кэш планировщика уже реализован. Проверки и ручной сценарий: [ship-order-planner-smoke.md](ship-order-planner-smoke.md).

Сверка 03.10.2026: **A–B готовы в коде; C–E — проект; F частично готов (кэш уже есть).** [Объективное ревью и основания статусов](proposals-review-2026-10-03.md).

Документ не меняет код, правила экономики или данные мира. Новые сохраняемые поля ниже — предлагаемое расширение, требующее отдельного согласования перед реализацией. Основной целевой runtime: Foundry 13.351 / Forbidden Lands 13.0.5 с сохранением совместимости Foundry 14.

## 1. Цель и рекомендуемый объём

В существующей вкладке корабля «Рейсы» игрок выбирает 1–3 заказа и сразу видит совместимый маршрут на уже импортированной карте рынка, расписание, загрузку, расходы и конечное положение. После отправки тот же интерфейс показывает принятый рейс и состояние корабля на его обработанное игровое время.

Первый выпуск сохраняет текущие правила: общий подход капитана, ручное решение в промежуточном порту, отдельные исходы заказов, существующие платежи. Автоматическое выполнение всей цепочки, новые правила сезонной навигации, произвольное число заказов и перестройка принятого рейса в этот выпуск не входят.

| Проекция времени | `scripts/engines/ships/voyage.js` | Есть чистые функции расписания и проекции; проверить соответствие округлению world-рейсов перед переиспользованием |

Главный пробел — связь между расчётом, картой и сохранённым рейсом. `routeTerms` возвращает путь по узлам, но теряет рёбра; составные `legOffer.quote` не фиксируют полную трассу и разбивку фаз. `worldShipTimeBreakdown` вычисляет время обработки заново по текущим данным портов. Этого недостаточно для исторически точного положения после изменения сети или экономики.

Сезонные данные есть у рыночных связей, но текущий корабельный `routeTerms` рассчитывает время из расстояния и скорости. Добавлять сезонные веса только в новый preview нельзя: результат разойдётся с исполнением.

## 3. Сценарий игрока

1. Открыть «Рейсы»: видны текущий порт, время корабля, состояние команды и доступные предложения.
2. Выбрать заказ флажком в видимой строке карточки, без раскрытия деталей. Одиночный и составной рейсы используют одинаковую модель выбора.
3. Сразу получить маршрут, сводку и доступность других сочетаний. При добавлении несовместимого заказа видеть конкретную причину и иметь возможность снять его.
4. Навести/выбрать заказ: подсветить его погрузку, доставку и участки, на которых он находится на борту. Выбрать остановку: показать связанные заказы.
5. Передвинуть ползунок прогноза или нажать «Следующая остановка»: увидеть предполагаемое положение, занятость трюма и ожидаемые операции.
6. Проверить итог, выбрать общий подход и бюджет, нажать «Принять и отправить». Только эта операция меняет состояние мира через существующий путь команд.
7. После отправки видеть действующий маршрут. В порту остаются привычные «Подвести итоги» и «Следующий порт» с ясным объяснением причины ожидания.

### Компоновка

- Верхняя строка: корабль, порт/участок, игровая дата корабля, краткая готовность.
- Слева: компактный список заказов. В строке — груз, погрузка → доставка, место в трюме, плата, выбор. Расходы одиночного заказа явно помечаются как отдельная оценка: их нельзя складывать для составного рейса.
- Справа: большая карта с выбранным маршрутом; под ней хронология остановок и шкала времени.
- Нижняя панель: число заказов, длительность, расходы, плата по договорам, плановая разница, рекомендуемый бюджет, конечный порт и основное действие.
- На узком окне блоки идут последовательно: выбор → сводка → карта → остановки. Доступен полноценный текстовый маршрут без взаимодействия с картой.

У каждого заказа устойчивые номер и цвет. Цвет дублируется номером/иконкой. Пройденный путь, текущий участок и прогноз различаются также толщиной/штрихом. Все кнопки имеют `type="button"`, подписи и клавиатурный доступ. Фокус, прокрутка, выбор и масштаб сохраняются при обновлении.

### Прозрачная сводка

Показывать раздельно:

- время полёта, обязательных портовых работ и известной задержки;
- груз на каждом участке, максимум загрузки и отдельное ограничение тайников;
- расходы, договорную плату до случайных исходов и плановую разницу;
- сумму, необходимую на борту, уже имеющиеся деньги и дополнительный перевод из казны;
- резервы на возвращение, стоянку и исходы, которые ещё не потрачены;
- конечный порт после последнего заказа; возвращение домой показывать отдельным прогнозом, оно не входит автоматически в принятый рейс.

Подсказка «ещё +N дней / +M расходов при добавлении» полезнее второй независимой сметы. Она рассчитывается сравнением всего плана до и после выбора.

## 4. Поиск маршрута

### Первая версия

Использовать существующий поиск кратчайшего воздушного пути между нужными портами. Кэшировать результаты для текущего снимка сети. Отдельно решать порядок операций: погрузка, перелёт, доставка, последующая погрузка.

Критерий подписывать явно: «Быстрее выполнить выбранные заказы». Сравнивать полное время с портовыми работами; при равенстве — расстояние, затем устойчивый порядок ID. Не обещать максимальную прибыль или минимальный риск.

Текущий перебор уникальных портов покрывает только часть допустимых рейсов. Например, обменные заказы A → B и B → A требуют повторного посещения A. Поэтому до заявления о глобальном оптимуме выбрать один из двух вариантов:

1. Быстрый выпуск сохраняет текущие ограничения и прямо сообщает: «Маршрут с повторным заходом пока не поддерживается».
2. Рекомендуемая законченная версия использует поиск по состояниям `(текущий порт, маска погруженных заказов, маска доставленных заказов)`. Переход — допустимая погрузка/доставка и перелёт; проверяются трюм и тайники. Повторный порт разрешён только при полезной операции. При 1–3 заказах пространство невелико, достаточно точного поиска с отсечением худших состояний.

Во втором варианте потребуется согласованно обновить планировщик и исполнение остановок: они должны пользоваться явными `pickupOfferIds` / `deliveryOfferIds`, а не автоматически выполнять все операции порта при каждом посещении. Критерий оптимума действует внутри явно описанных правил погрузки и остановок.

Разгрузка перед погрузкой в одной остановке освобождает трюм. Стоимость общей дороги и содержания учитывается один раз, выплаты и грузовые операции — по договорам. Простое прохождение узла графа не означает портовую стоянку.

Новые цели «Дешевле» / «Меньше риска» отложить до определения весов и обновления общего движка. Стиль капитана показывать отдельно от критерия маршрута. Доступность/срок предложений проверять по существующим правилам; не вводить новые дедлайны ради интерфейса.

## 5. Карта и геометрия

Рекомендуемая технология — существующий HTML/SVG-подход: фоновое изображение + SVG-рёбра, порты и маркеры кораблей. Для этой сети не требуется новая production-зависимость.

Выделить общий компонент просмотра карты, который получает подготовленные данные и не умеет сохранять каталог. Его используют окно корабля и карта рынка. GM-инструменты редактирования остаются отдельным слоем. Из общего компонента нельзя импортировать тяжёлый редактор в стартовый граф модуля.

Слои: фон → доступные связи → выбранная трасса → порты/номера остановок → корабль → подсветка выбранного заказа. Добавить «Показать весь рейс», «К кораблю» и легенду. Пользовательский pan/zoom хранить локально, без записи настроек мира.

Сопоставлять маршрут с геометрией по точным рёбрам `(from, to, routeId)`, включая параллельные связи. При обратном движении разворачивать `pathPoints`. Длительность и порядок прохождения рёбер определяются игровыми расстояниями; позиция внутри ребра — интерполяцией по длине его ломаной. Пиксельная длина разных рёбер не заменяет их вручную заданные километры.

Учесть:

- Фон отсутствует или недоступен: остаются порты, линии и текстовый маршрут с сообщением о фоне.
- Узлы не расставлены: использовать существующую схематическую раскладку с явной пометкой, что положение условное.
- Дом и рынок могут соответствовать одному региональному узлу. Не создавать фиктивные расстояния на карте; перелёт внутри региона отображать условно, если отдельных координат нет.
- Несколько кораблей/остановок в одной точке: объединённый значок с раскрытием, без записи визуальных смещений в координаты мира.
- У игрока отображаются только доступные ему корабли и данные. Проверки видимости применяются до подготовки контекста, а не только через скрытые элементы шаблона.
- Если сама импортированная картинка содержит GM-секреты, SVG-фильтр их не скроет. Для общего просмотра нужен разрешённый игрокам фон.

## 6. Время и положение

Разделить три режима: «Состояние корабля», «Прогноз» и необязательное «Проиграть маршрут». Всегда подписывать дату выбранного режима.

Фактическое положение выводить из обработанного состояния корабля (`timelineQd`, активный участок и его обработанное время), используя существующие правила времени. Дата поселения сама по себе не разрешает пролететь следующие остановки: корабль может ждать решения в прошлом относительно поселения.

Прогноз будущих участков предполагает отправление сразу после обязательных работ и решения игрока; эта условность подписывается. Неизвестные события и длительность добровольного ожидания заранее не вычисляются. После фактического исхода прогноз оставшегося пути обновляется.

В порту маркер остаётся неподвижным во время погрузки, выгрузки, обязательной передышки, задержки или ожидания решения. Обычный ночной отдых уже включён в скорость корабля; нельзя добавлять его второй раз.

Расписание строится в QD (четвертях дня), а анимация между отметками лишь плавно показывает положение. Она не двигает календарь, не вызывает команды, не бросает исходы и не списывает деньги. Для режима уменьшенной анимации оставить ползунок и шаги по остановкам.

Особенно важно сохранить существующее округление: разбивка одного перелёта на несколько рёбер не должна увеличивать его длительность из-за отдельного округления каждого ребра. Сумма фаз должна точно совпадать с утверждённым `quote.durationQd`.

## 7. Данные и устойчивость принятого маршрута

### Без изменения хранения

Первый этап может строить временный `preview` из текущих предложений, корабля и карты. Выбор, масштаб и позиция ползунка — состояние интерфейса. Открытие окна и просмотр не изменяют данные мира.

Для старого активного рейса допустима только помеченная реконструкция по текущей сети. Если восстановить трассу нельзя, показать известные начальный/конечный порты, остаток времени и статус «точное положение недоступно», без выдуманного точного маркера.

### Предлагаемое расширение для точного движения

После отдельного согласования формата добавить необязательный версионированный снимок навигации в принятую смету физического участка; аналогично — в будущие участки `orderBundle`:

- последовательность узлов и конкретных `routeId`;
- расстояние каждого ребра;
- фазы и их относительные границы QD: погрузка, полёт, портовые работы;
- геометрию трассы и систему координат/идентификатор версии карты, если требуется неизменное отображение после редактирования сети.

Окончательные имена и вложенность определить в отдельном контракте. Не сохранять постоянно меняющиеся `ship.x/y`, проценты или тики анимации: они вычисляются из снимка и времени.

Один снимок формируется авторитетным GM после проверки заказа. Локальный preview не является источником принятой геометрии, стоимости или времени. Новые записи получают снимок; старые не переписываются при загрузке. Split storage и commit-marker recovery остаются прежними.

Нужно явно выбрать политику замены фоновой карты: если новая картинка имеет другую географическую привязку, даже сохранённые координаты нельзя молча накладывать на неё. Показывать несовпадение версии и текстовый маршрут либо использовать доступный исходный фон. Сам URL файла не защищает от замены изображения по тому же пути.

Общий UI для одного и нескольких заказов не требует объединять все legacy-операции исполнения: использовать адаптер к действующим одиночным и составным командам.

Пересчёт preview запускается при изменении выбора/стиля и значимых данных, а не на каждом кадре/hover. Кэш зависит от выбранных ID, параметров корабля, его времени и позиции, актуальных предложений и ревизии каталога/поселения. Проверку доступности соседних сочетаний вычислять по требованию либо переиспользовать результаты.

При асинхронном вычислении устаревший результат не должен заменять более новый. На время пересчёта старая карта явно помечена как устаревшая, отправка недоступна. Если GM обнаружил изменение исходных данных, показать обновлённый план и потребовать нового осознанного подтверждения; не отправлять молча по другой смете.

## 9. Этапы реализации и критерии готовности

### Этап A — контракт preview и проверка существующего расчёта

**Готово в коде.** Единый preview покрыт `ship-order-preview-check.mjs`; точного фазового расписания ещё нет.

Определить единый временный результат: остановки, рёбра, расписание, загрузка, экономика, конечный порт, блокирующие причины. Зафиксировать модель повторных портов, фаз и округления. Подготовить независимые сценарии одного, двух и трёх заказов.

Готовность: preview воспроизводит текущую смету и порядок операций, не меняет исходные объекты, деньги, календарь и случайные исходы.

### Этап B — интерактивный выбор и маршрут без изменения хранения

**Готово в коде.** Выбор, смета, карта и отправка реализованы; живая проверка UI остаётся пользовательской.

Обновить карточки, общую сводку, показ загрузки и остановок. Подключить общий просмотр существующей карты и точные рёбра рассчитанного preview. Сохранить нынешнюю отправку и предел 3 заказа.

Готовность: выбор сразу отражается на карте; игрок понимает причину несовместимости, конечный порт и дополнительный бюджет до отправки. Это первый самостоятельно полезный выпуск.

### Этап C — прогноз времени

**Проект.** Точные фазы и ползунок не реализованы; сначала требуется единая модель портовых работ и ожиданий.

Добавить фазы, ползунок, переходы по остановкам и просмотр конечного положения. Сопоставить время и геометрию, включая удалённую погрузку и ожидания.

Готовность: маркер не движется во время портовых работ, после последней доставки остаётся в конечном порту; preview не исполняет операции.

### Этап D — согласованный снимок навигации и фактическое движение

**Проект.** Порты/смета/время сохраняются; устойчивый снимок геометрии и проекция позиции отсутствуют.

После согласования расширения хранения фиксировать навигационные данные для новых отправлений; покрыть продолжение составного рейса, возвращение, передислокацию и совместимость собственного исходящего груза. Для ручных рейсов без привязки к мировой сети оставить текстовый показ.

Готовность: перезапуск клиента и изменение каталога не меняют утверждённые время/трассу; старые рейсы работают без миграции и честно обозначают точность реконструкции.

### Этап E — корабли на общей карте рынка

**Проект.** Слой фактических кораблей на общей карте зависит от согласованной проекции D.

Подключить тот же слой кораблей к карте рынка: текущий корабль, выбранное доступное судно, открытие его окна. Синхронизировать отображение после подтверждённых операций и продвижения игрового времени.

Готовность: окно корабля и карта рынка показывают одно состояние на одну и ту же дату; игрок не видит чужие закрытые сведения и не может редактировать сеть.

### Этап F — оптимизация и дополнительные удобства

**Частично.** В `ship-order-planner.js` уже есть кэш расчёта/карты. Дополнительные удобства — проект; новая оптимизация требует замеров.

По фактическим замерам добавить кэширование/частичную отрисовку. Затем — сравнение прибавки от заказа, необязательное проигрывание, расширенные фильтры. Worker рассматривать только если измеренный расчёт блокирует UI; Canvas/WebGL — только если SVG перестаёт справляться с реальной сетью.

Увеличение лимита заказов, ручной порядок портов, другие критерии оптимизации и интеграция с отдельной Foundry Scene — самостоятельные следующие задачи. Для импортированного фона внутри карты рынка Scene и перемещение Token не требуются.

## 10. Проверки

### Сценарии расчёта

Один заказ с местной/удалённой погрузкой; два заказа с общим участком; три заказа с разными портами; освобождение трюма перед погрузкой; превышение общей/скрытой вместимости; разорванная сеть; параллельные связи; обратное движение по ломаной; одинаковые оценки маршрутов; повторный порт согласно выбранному контракту.

### Время и сохранность

Границы каждой фазы; нулевая/короткая фаза; округление QD; транзит без стоянки; задержка события; отсутствие денег; ожидание исхода; отставание корабля от даты поселения; перевод календаря назад; изменение/удаление связей; изменение изображения; старый рейс без снимка. На всех preview-сценариях — отсутствие мутаций, выплат и бросков.

### Команды и доступ

Игрок с правами управления/только чтения/без доступа; отсутствие authority-GM; конфликт ревизии; предложение уже занято; повтор команды; повторное открытие окна; сохранение фокуса и черновика. Проверить отсутствие прямой записи player-клиентом в world settings и двойных списаний/выплат.

### Статические проверки при реализации

- Сначала узкие `ship-multiorder-check.mjs`, `ships-runtime-characterization-check.mjs`, новые проверки планировщика/проекции.
- `npm run routes:check` для геометрии и общих компонентов карты.
- `npm run ships:check` после интеграции корабельных сценариев.
- `npm run suite:storage` и при необходимости `storage:batch:check` при изменении сохранения/команд.
- `npm run ui:check`, `npm run css:check` после шаблонов и стилей.
- `npm run compat:check`, `npm run lazy:check`, `npm run lint` для соответствующих изменений.
- `npm run market:check` при затрагивании рыночных перевозок/собственного исходящего груза.
- `npm run perf` при диагностике отзывчивости; `npm run perf:budget` после стабилизации изменений.

Ручная Foundry-проверка остаётся отдельной: GM и игрок одновременно выбирают/наблюдают рейс, проходят остановку, разрешают исход, продолжают путь, сверяют карту и деньги. Проверить фон с сетью 100–200 связей, узкое окно, обе темы, масштаб/панорамирование, повторное открытие, Foundry 13 и 14. Статические проверки не подтверждают работу этих UI-сценариев.

## 11. Решения для начала работы

Рекомендуемые defaults: вкладка «Рейсы», максимум 3 заказа, критерий времени, существующий SVG и импортированный фон, локальный preview, ручные решения в портах, отсутствие автоматического возвращения. A–B завершены; продолжение разделить на проверяемые изменения C → D → E, F — по конкретной потребности.

Отдельного решения требуют только изменение сохраняемого формата для точной навигации и расширение действующих правил, например повторные заходы. Проектирование этих изменений допустимо сейчас; этот план сам по себе не разрешает запись новых данных в Foundry-мир.
