# Составные корабельные рейсы: контракт первого внедрения

Статус: поле `ship.orderBundle` отдельно согласовано пользователем 22 сентября 2026 года. Первый этап реализован в коде; ручной сценарий в Foundry ещё не выполнен. Этот документ не разрешает миграцию или изменение данных мира.

## Что делает игрок

На стоянке выбрать от одного до трёх свободных заказов, общий подход капитана и бюджет. До подтверждения показать порядок портов, занятость трюма на каждом участке, общее время, общий расход и оплату каждого договора. Система ищет короткий допустимый порядок погрузок и доставок по существующим воздушным связям; доставку нельзя поставить раньше погрузки. Не смешивать грузы заказчиков со складом поселения. Каждый принятый договор имеет свой зафиксированный груз, плату, стиль, исход и изменение внимания.

При отправке только одно судно и команда уходят из поселения, бюджет переводится один раз. За общий перелёт, питание, жалованье и эксплуатацию деньги списываются один раз на каждом физическом участке; погрузка, разгрузка и портовые сборы учитываются по партиям. Фактический заход в порт занимает не меньше одного дня; передышка ядра идёт одновременно с грузовыми работами, поэтому длительности не складываются. При промежуточной стоянке выполняются операции этого порта и выплачиваются только доставленные заказы. Затем игрок решает, когда отправляться в следующий запланированный порт. Ожидание сверх передышки оплачивается по действующим правилам. После последней доставки составной рейс закрывается, а судно может взять новый заказ или вернуться домой.

Техническая остановка без погрузки и доставки, случайное предложение в промежуточном порту, добавление нового заказа к уже отправленному рейсу и правила дальнего непрерывного полёта остаются следующим развитием. Первый этап уже поддерживает несколько одновременно принятых заказов и несколько портов их исполнения; частота появления новых заказов и величина выплат остаются нынешними.

## Дополнение формата

Единственное новое сохраняемое поле — необязательное `ship.orderBundle`. Его нет у прежних судов и прежних рейсов. Оно создаётся только при принятии двух или трёх заказов одновременно и удаляется после исполнения последнего заказа и возможной задержки. Структура (без служебных сумм и меток времени):

```js
ship.orderBundle = {
  id: "ID первой операции отправки",
  orders: [{
    offerId: "ID принятого предложения",
    offer: { /* неизменяемые условия: пункты, груз, награда, смета */ },
    style: "normal", // или осторожно / с риском
    state: "waiting-pickup", // loaded / delivered
    outcome: null,          // зафиксированный бросок перед проверкой денег
    outcomeApplied: false,
    deliveredAtQd: null
  }],
  stops: [{
    point: { kind: "market", id: "...", regionId: "...", label: "..." },
    pickupOfferIds: [],
    deliveryOfferIds: [],
    legOffer: { /* замороженная смета физического участка */ }
  }],
  nextStopIndex: 0,
  status: "travelling" // at-port / awaiting-outcome
};
```

`ship.activeVoyage` по-прежнему описывает только текущий физический участок и остаётся совместимым со старыми одиночными рейсами. В составном рейсе его `quote.contract` пуст, поскольку договоры хранятся в `orderBundle.orders`. Между участками `activeVoyage` равен `null`, но `orderBundle` остаётся до выполнения всех договоров. Уникальные ID денежных операций включают ID рейса, участка и договора; повтор сокет-команды или расчёта десятника не списывает расходы и не выдаёт плату вторично. Заказы записываются в существующий формат истории и сводного отчёта. Старые записи не переписываются.

В первой версии общий подход капитана выбран для всего составного рейса. У каждого заказа отдельные коммерческие кубики и результат, но дорожное происшествие бросается только для одного договора в порту доставки: его задержка и расходы действуют на судно один раз. Ожидание средств сохраняет уже выпавший результат. Пассажиры и почта резервируют 20% трюма; новая ставка учитывает, что это попутное место, а не исключительный найм всего корабля. Премия рискованного подхода за своевременное исполнение не выдаётся другим заказам в том же порту после общего происшествия с задержкой. Рекомендуемый бюджет включает запас на исходы, который остаётся на борту до фактической траты; подробности — в [балансе заказов](ship-order-balance.md).

Пока `orderBundle` существует, прежние команды одиночного заказа, возвращения домой, удаления судна и правки состава не должны обходить обязательства. Нехватка бортовых денег для события или следующего участка показывает конкретный долг и не теряет уже сохранённый исход. Результат заказа, направление внимания, груз и уже проведённые суммы не меняются из-за обновления рынка. Нормализация старого состояния не создаёт составной рейс и не переписывает одиночный.

## Проверка

Офлайн-проверки: два заказа с разными пунктами доставки, удалённая погрузка, превышение трюма на промежуточном участке, невозможный маршрут, нехватка денег на следующую ногу, повтор команды/расчёта, одно дорожное происшествие на общий участок, отдельная плата и внимание, возврат прежнего одиночного рейса без изменений. Сокет и права ГМа/игрока проверяются существующим путём ship-operation. Ручная проверка Foundry остаётся за пользователем: выбрать 2–3 заказа, пройти промежуточный порт, дождаться/подвести итоги, продолжить и сверить казну и отчёт.
