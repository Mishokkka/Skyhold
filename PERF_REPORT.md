# Аудит производительности: результаты и открытые направления

Исторический срез **23 августа 2026 года**, модуль 2.0.0. Сокращён 3 октября: сохранены результаты, методика и незавершённые направления; номера строк старого кода и повторный план уже выполненных исправлений удалены. Статусы ниже относятся к августовскому аудиту и требуют сверки перед новой работой.

Основные команды, fixtures, бюджет и runtime observer описаны в [performance baseline](docs/performance-baseline.md). Ручные проверки — в [Foundry smoke matrix](docs/manual-foundry-smoke-matrix.md).

## Что установил аудит

Storage-бюджеты проходили, но не покрывали стоимость контекстов ApplicationV2, Handlebars, DOM, layout, heap и многоклиентского обновления. Основные подтверждённые потери были в производной UI-модели:

- карточки строений готовили редакторские структуры до фильтрации; на 500 жителях/200 зданиях — примерно 0,7–1,0 с и 85,1 MiB сериализуемого контекста;
- строки жителей создавали варианты работы `жители × здания`: 102 000 вариантов и 20,61 MiB на large, 204 000 и 41,22 MiB на extreme;
- кэш удерживал контексты старых ревизий, холодное чтение повторяло hashing, транзакции использовали слишком широкий scope;
- малое изменение всё ещё передавало целиком изменённый world-setting раздел, широкая invalidation затрагивала другие окна.

Без живого профиля не объявлялся P0 или точное время отклика Foundry. Крупнейший подтверждённый выигрыш дали лёгкие карточки, подготовка полей редактора по требованию и кэш текущей ревизии.

## Результаты исправлений августа

| Статус | Finding | Результат и граница сохранения UX |
|---|---|---|
| Исправлено | PERF-01 | Карточки зданий фильтруются до editor-подготовки и используют один общий список складских помещений. Полная модель редактора и итоговые отображаемые значения защищены отдельным контрактом. На fixture `500/200`: сериализуемый контекст уменьшился примерно с `85,09 MiB` до `0,68 MiB`; warm-подготовка — до `10,84–14,40 ms`. |
| Исправлено | PERF-02 | Контекст жителей переведён с `P × B` на `P + B`; editor-only поля создаются только для открытого редактора. Нативный `select` получает общий каталог синхронно перед открытием, поэтому mouse/keyboard-сценарий и текущие/custom/injured значения сохранены. На fixture `1000/200`: p95 `6,76 ms`, около `1,18 MiB`. |
| Исправлено | PERF-03 | Derived-context cache очищает прошлое поколение при смене revision; повторное использование внутри текущего revision сохранено. |
| Исправлено | PERF-04 | Split-storage повторно использует уже вычисленные hashes и не хеширует default/legacy разделы до фактической необходимости. Порядок записей, commit-marker recovery и legacy fallback не изменены. Cold-read p95 на тех же fixtures снизился примерно до `197/311/309 ms`. |
| Исправлено | PERF-05 | Все прямые app-транзакции получили явный минимальный scope; операции, действительно меняющие оба раздела, оставлены `both`. Строгий AST-контракт проверяет 53 call sites. |
| Исправлено | PERF-08 | Tooltip сохраняет прежнее содержимое и появление у цели, но больше не выполняет geometry/style hot path на каждом `mousemove`. |
| Исправлено | PERF-09 | Пересчитываются только изменившиеся trait cells, работа объединяется в один animation frame; observer lifecycle закрывается вместе с окном. |
| Исправлено | PERF-10 | Storage search использует подготовленный индекс и материализует не более 50 совпадений, показывая полный total и признак продолжения. Переход к комнате/строке и search semantics сохранены. |
| Частично исправлено | PERF-11 | 14 доказанно read-only потребителей переведены с `get()` на `view()`. Mutable/draft потребители намеренно продолжают получать clone, чтобы не менять isolation contract. |
| Исправлено | PERF-14 | UUID разрешаются с deduplication и bounded concurrency `4`; исходный порядок строк, сопоставление документов и validation errors сохранены. |
| Исправлено | PERF-15 | Biography sanitization перенесена с каждого символа на `change`/paste/save, а appearance autosize объединён через rAF. Итоговая сохранённая строка проходит прежний sanitizer. |
| Исправлено | PERF-16 | Поиск шаблонов фильтрует уже созданные карточки без полного Application render; отложенная работа отменяется при close. Empty-state разделяет отсутствие шаблонов и отсутствие совпадений. |
| Исправлено | PERF-17 | Eager preload сокращён с 45 до 21 core partial; building editor, unique buildings и mass combat загружают свои группы перед первым context/render. Рекурсивный контракт проверяет полноту partial-графа и lazy consumer boundaries. |
| Исправлено | PERF-18 | Market context строит purchase plan один раз после окончательного quote/room resolution. Итоговый plan и сообщения валидации не изменены. |
| Исправлено | PERF-19 | Appearance ResizeObserver, pending frame и ссылки на textarea освобождаются при render/close. |
| Исправлено | PERF-20 | Закрытие building/unique editor обновляет manager только при накопленном внешнем изменении; обычный close без изменений сохраняет окно и focus без лишнего render. |
| Исправлено | PERF-22 | Focus keeper использует weak DOM references и забывает закрытый frame даже без последующего manager render. |
| Отложено намеренно | PERF-06, PERF-07 | Дробление persisted settings и scoped cross-client invalidation требуют отдельного storage/socket design, миграции и живого GM+player proof. Формат данных и существующий broadcast contract не менялись. |
| Отложено намеренно | PERF-12, PERF-13 | Player/GM authority, revision/idempotency и глобальная write queue не ослаблялись. Двухфазная Document-I/O схема без runtime failure/compensation тестов была бы рискованнее подтверждённого выигрыша. |
| Отложено намеренно | PERF-21, PERF-23 | Compositor layers и Actor Item merging нельзя безопасно оптимизировать без живых Paint/Layers и system-document semantics. Визуальный граф и инвентарь оставлены без изменений. |

Исторически прошли check, storage, perf:budget/perf:check, lint, CSS/UI, market, compat/lazy и socket characterization. Browser smoke августа не выполнен; эти результаты не являются проверкой текущего кода 3 октября.

## Диагностический бюджет августа

| Fixture | Clone p95 | Normalize p95 | Hash p95 | Cached read p95 | View p95 | Holdings write p95 | Catalog write p95 | No-op p95 | Speedup |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| medium | 8,24 ms | 178,78 ms | 14,46 ms | 7,97 ms | 0,10 ms | 85,11 ms | 108,80 ms | 103,83 ms | 11,4× |
| large | 14,37 ms | 251,91 ms | 33,11 ms | 22,65 ms | 0,08 ms | 214,66 ms | 160,98 ms | 199,23 ms | 7,5× |
| extreme | 20,00 ms | 211,47 ms | 36,20 ms | 22,88 ms | 0,09 ms | 270,87 ms | 157,70 ms | 238,44 ms | 10,9× |

На изменённый один раздел приходились две meta-записи и одна partition-запись, на no-op — ноль. Обе meta-записи нужны commit-marker recovery; dual-partition commit требует согласованного rollback snapshot.

Среда: Windows 10.0.19045, Ryzen 7 5800H, 15,4 GiB RAM, Node 24.16.0/npm 11.13.0. Fixtures: medium 100/50/100, large 500/200/500, extreme 1000/200/1000 жителей/зданий/складских строк. Серии benchmark короткие: 12 итераций, extreme 8, write samples 4/3; p95 близок к максимуму, это regression gate, не статистика production.

## Сохранённые направления дальнейшей работы

Это предложения августовского аудита. Перед реализацией проверить текущего владельца и измерить, остаётся ли проблема. Согласование нового формата хранения и операций с миром требуется отдельно.

| Направление | Условие и границы |
|---|---|
| PERF-06: меньшие persisted-разделы | Сначала измерить сеть/settings на GM+player после исправления UI. Per-holding/delta layer потребует migration, recovery manifest, rollback, лимитов и плана V13/V14 |
| PERF-07: точечная invalidation | Revision/scope/holding — подсказки, источник данных остаётся settings. Старый/неизвестный payload вызывает полное обновление; зависимости окон должны быть явными |
| PERF-11/12: чтение и подготовка player patch | Только доказанно read-only пути переходят на view(). Минимальный patch не отменяет GM validation, permission categories, operationId, revision/base values и command-result |
| PERF-13: внешнее Document I/O вне очереди | Нужен двухфазный/compensation design с повторной проверкой ревизии перед mutation. Простое перемещение await за очередь создаёт race |
| PERF-21: compositor layers | Paint/Layers trace должен подтвердить вред постоянного will-change и эффект изменения CSS; убрать визуальный эффект без измерений недостаточно |
| PERF-23: рост Actor Items | Сначала измерить сотни выдач и задержку листа. Слияние Items может менять системную семантику и требует отдельного решения |
| UI-контекст и виртуализация | Измерять p50/p95, число строк/options, объём контекста и heap. Виртуализацию вводить лишь при оставшихся DOM long tasks, сохраняя клавиатуру, фокус и раскрытия |
| Оставшиеся локальные кандидаты | Проверить requestAnimationFrame в WindowFrameMixin, autosize textarea, parsed geometry графа, последовательность открытия десятника и прямые рендеры mass-combat. Эти наблюдения не доказывают текущий дефект |

Не оптимизировать без профиля обходы map/filter, редкие UUID, сортировку нескольких GM или CSS-тени. Не удалять recovery-записи, не увеличивать лимит кэша и не ослаблять retry/revision проверки ради числа миллисекунд.

## Живое профилирование

Датированные Node-замеры не показывают FPS, DOM/style/layout, реальные settings frames, core Document I/O или освобождение окон. Сценарии для повторной проверки:

1. Жители: cold/warm open, поиск/фильтры, 30 назначений; здания: категории и 20 редакторов с/без изменений.
2. Склад: 1k/5k/10k строк и длинный поиск; ввод не пишет settings. Tooltip/resize — geometry reads, forced layout и observer callbacks.
3. Долгая сессия: 100 open/edit/close, 500 renders, периодические GC snapshots; проверить выход heap на плато.
4. GM + несколько игроков: правка holdings, catalog и player-команда; количество writes/messages, WebSocket bytes и render requests/completed по окнам.
5. Documents: 100/500 выдач, multi-UUID покупка и параллельная независимая запись; число Items и ожидание очереди.
6. Startup: холодный кэш, запросы/компиляция шаблонов, первое/повторное открытие lazy-окна. Дополнительно — DOM-богатый мир с Actors/Items/Tokens/Scenes/компендиумами, которого нет в fixtures.

Фиксировать версии Foundry/системы, роль, состав владения, точную последовательность действий и p50/p95. Одна запись observer не смешивает навигацию, десятник, импорт и бой. После изменения данных/normalizers обновлять baseline только по воспроизводимому замеру; passing budget не заменяет GM/player smoke в Foundry 13/14.
