# FBL Skyhold Manager

Документация и статусы проектов: [указатель](docs/README.md). Действующий каталог зданий: [v16 и условия применения](docs/morale-v16-implementation.md).

Личный модуль менеджмента владений для Forbidden Lands в Foundry VTT.

Поддерживаемая среда: Foundry VTT `13` и `14` (`verified: 14.364`), система `forbidden-lands` от `13.0.0` до проверенной линии `14.0.4` без искусственного `maximum`. На Foundry V13 используется системная ветка 13.x, на Foundry V14 — ветка 14.x.

Runtime использует namespaced Foundry API через `scripts/integrations/foundry-runtime.js`. Команда `npm run compat:check` блокирует deprecated globals, удалённые V12 compatibility shims, старые Handlebars helpers и приватные Canvas/PIXI-зависимости, поэтому один кодовый путь продолжает работать на V13 и готов к V14.

Модуль предназначен для ведения поселений, кораблей, аванпостов, организаций и островов-летяг. Главная задача: держать жителей, здания, склад, экономику, оборону и события владения в одном окне, без ручных таблиц рядом с Foundry.

## Установка

1. Распакуй модуль в папку `Data/modules/fbl-skyhold`.
2. Проверь, что файл `module.json` лежит прямо внутри `fbl-skyhold`, а не во вложенной папке.
3. Включи модуль в мире Foundry.
4. После загрузки мира используй кнопку модуля или API `game.fblSkyhold.open()`.

## Что умеет модуль

Модуль хранит несколько владений одновременно. Тип владения может быть поселением, кораблем, аванпостом, организацией или островом-летягой.

Основные вкладки владения: обзор, жители, здания, оборона, особое, склад, внешний рынок и GM. Корабельные рейсы открываются через «Внешний рынок», Политика — отдельной кнопкой в шапке.

Игроки могут видеть публичные владения. Скрытые GM-владения не должны открываться через обычные окна, редакторы и сценические отметки.

## Обзор владения

В обзоре хранятся статус, период, публичное описание, заметки, население, мораль, репутация, Defence Rating, погода, высота, дрейф, механизмы и развитие.

Развитие делится на четыре направления:

- еда;
- технология;
- культура / религия;
- война.

Здания могут добавлять развитие. Жители напрямую развитие не повышают, они работают через здания, бригады, оборону и производство.

## Жители

Житель хранит имя, народ, пол, возраст, культуру, веру, социальное прошлое, черты, работу, жилье, зарплату, мораль, ранения и статус смерти.

Возраст нормализуется по народу. Используются категории вроде молодой, взрослый и старый, но возраст хранится числом.

Жители могут быть назначены:

- в здания;
- в жилье;
- в строительные бригады;
- в оборонные отряды;
- командиром обороны.

При удалении жителя модуль чистит ссылки на него в зданиях, бригадах и обороне.

Планировщик работников рассчитывает назначения на клоне владения, показывает список и очищаемые слоты до записи, а при подтверждении проверяет неизменность исходных данных. Применённый план получает operation id и запись в общем журнале операций.

## Здания

Здания бывают обычными объектами владения, а не только шаблонами. Шаблон используется как заготовка, после постройки объект живет отдельно и может быть отредактирован.

Здание может иметь функции:

- производство;
- доход;
- оборона;
- жилье;
- склад;
- культура / религия.

Поддерживаются рабочие места, подходящие типы работников, эффективность, строительство, ремонт, повреждения, содержание, материалы, требования по развитию, религиозные настройки, производственные линии и внутренние складские помещения. Начиная со схемы 54 жизненный цикл (`planned/building/active/disabled/abandoned`) отделён от физического состояния (`intact/damaged/heavilyDamaged/destroyed`), а ремонт хранится как самостоятельный процесс. Старое `constructionStatus` сохраняется как совместимая проекция.

Лечебные здания получают медицинский блок, но обычная загрузочная нормализация больше не должна стирать пользовательские функции здания. Жесткое восстановление медицинского профиля вынесено в repair-режим.

## Строительство

Строительство использует материалы, сложность, цель успехов, прогресс и строительные бригады.

Бригады могут иметь участников, лидера, подходящие типы работников и временное распределение по объектам.

Если здание или житель удаляется, связанные назначения чистятся, чтобы в данных не оставались мертвые ID.

## Склад

Склад хранит ресурсы, предметы, деньги и лог операций.

Глобальный поиск находит ненулевые ресурсы и предметы сразу во всех помещениях и переводит интерфейс к найденной комнате. Ресурсы и предметы можно выбрать чекбоксами, выбрать целевую комнату и сначала увидеть рассчитанное размещение. Подтверждённый batch применяется с revision guard и operation id; предмет перемещается как неделимый stack, а его количество читается через Forbidden Lands adapter `system.quantity`.

Из GM-вкладки каталог открывается отдельным полноразмерным окном. Оно показывает пользовательские и все встроенные ресурсы, поддерживает поиск и карточное редактирование. Кнопка «Настроить» создаёт мировое переопределение встроенной записи; WebP-изображение можно выбрать через Foundry FilePicker. «Восстановить» удаляет только переопределение. Каталожное изображение имеет приоритет над старыми путями, ранее сохранёнными непосредственно в строках склада.

Игроки берут и отдают вещи только через своего дефолтного персонажа. Модуль использует `game.user.character`, а если он не назначен, пробует выбранный токен как fallback.

Выбор актера в складском интерфейсе намеренно отсутствует. Это снижает шум и не раскрывает игрокам лишних актеров мира.

Склад поддерживает:

- ресурсы с количеством;
- предметы с сохранением item data;
- складские комнаты;
- отметку “на продажу”;
- казну в медных монетах с отображением в ЗМ / СМ / ММ;
- лог операций.

Основные вкладки, storage subtabs и batch controls имеют mouse target не меньше 32 px. Клавиатура нужна прежде всего для ввода значений в поля; основные сценарии не требуют keyboard-only управления.

## Экономика

[Единый контракт](docs/economy-contract.md) задаёт деньги, ресурсы, пищу, труд, содержание, стройку, склад и торговлю. Десятник равен 40 QD. Кнопка в шапке готовит расчёт на отдельном снимке: «Сводка», «Хозяйство», «События», «Точный diff». До подтверждения мир не меняется; изменение владения или влияющего каталога требует пересчёта. Экономика, лечение/возраст, часы, события и отчёт применяются одной транзакцией к выбранному владению. Случайные исходы раскрываются после записи; подробности остаются в окне, чат получает короткую публичную карточку.

На обзоре видны запас еды на десять дней, незаполненные работы/бригады, повреждения и лечение. Производство использует целые QD и FIFO-партии конкретных ресурсов либо допустимой категории; дорогой запас можно защитить от подстановки. Внутренний спрос имеет конечный общий бюджет: повторы торговых зданий расширяют мощность, непроданное остаётся на складе. Прибывшая в текущем Apply внешняя поставка продаётся локально со следующего десятника; мгновенная доставка между Apply доступна в первом следующем расчёте.

«Внешний рынок» открывает покупки, продажи и обзор кораблей. Ассортимент складывается из общего каталога, страны, размера/состояния и специализаций точки, организаций. Stock и отдельный demand сохраняются между открытиями и восстанавливаются за 2–6 десятников; организации не создают копий запаса. Доступность зависит от региона владения и сети маршрутов, которую ГМ редактирует на карте с сезонностью и калибровкой расстояний.

Перед сделкой видны товар, фрахт, обработка, страховка, пошлина, срок и риск. Входящая поставка может делиться на партии. Исходящая резервирует FIFO-товар до отправки, выручка начисляется по доставке; needsResolution останавливает только затронутую партию до решения ГМ. Подтверждение ГМа/игрока идёт через authority-GM с ревизией, operationId и атомарными резервами/оплатой. [Контракт рынка](docs/external-market-contract.md), [каталог ресурсов](docs/economy-resource-catalog.md), [торговый лор](docs/air-islands-trade-lore.md) уточняют технические и игровые правила.

Нагрузка ресурса одинакова на складе, в доставке и на корабле; старые переопределения предложения не меняют её. Ввозная пошлина берётся в стране назначения с местной надбавкой, вывозная — в стране отправления, отдельно и по умолчанию 0. При продаже рынок покупателя является импортирующей стороной. Самый дешёвый допустимый путь рассчитывается для выбранного груза и вместимости; УРС ограничивает доступ. Слишком большой денежный заказ нужно разделить, его сумму не обрезают после подтверждения. Торговый режим страны пока описателен, организационная репутация не меняет сделку; дальнейшие правила отмечены в [плане торговли](docs/trade-market-remediation-plan.md).

Полный reset Лапуты уже завершён по сообщению владельца мира. Обновление зданий — отдельный [Preview/Apply v16](docs/morale-v16-implementation.md#применение-пользователем), который работает с текущим сохранением и не повторяет reset.

## Корабли и Политика

«Внешний рынок» показывает флот; отдельное окно судна содержит заказы, экипаж, финансы и GM-настройки. Доступны мировой цикл, 1–3 совместимых договора, собственное время и продажа складского товара своим кораблём. Дома экипаж отдыхает на борту; выход на береговую работу требует явного действия. [Правила кораблей](docs/ships-world-stage.md), [дальнейшие этапы](docs/settlement-ships-implementation-plan.md).

Политика открывается отдельной кнопкой: Контроль, кабинет, курс и история. Реализованы GM-операции, каталог общих/личных вариантов и эффекты десятника. Пакетный расчёт, действия игроков и расходование карт требуют продолжения; [контракт v1](docs/politics-v1-contract.md) отделяет эти проекты от действующего кода.

## События, автоматизация и журнал операций

Случайное событие может содержать декларативные эффекты для ресурсов, казны, развития и модификаторов владения. Перед применением модуль строит preview на клоне и атомарно проверяет отрицательные ресурсы и расходы казны. Событие можно применить сразу, запланировать на следующий период или архивировать. В workflow десятника выпавшие события сохраняются bounded bundle, GM-only текст не попадает в публичную карточку, а эффекты остаются явно отмечены как ожидающие отдельного решения GM.

Общая operations timeline собирает структурированные ходы десятника, планы работников, эффекты и расписание событий, последствия боя и импорт контента. Payload десятника хранит ограниченные по размеру секции экономики, точного diff, выпавших и подошедших событий вместе с исходными счётчиками. Повторная команда с тем же operation id не должна создавать вторую запись или повторный side effect.

## Content packs

GM-вкладка импортирует versioned JSON packs с шаблонами зданий, пользовательскими ресурсами, событиями, рыночными локациями, характерами стран, специализациями, организациями, размерами/состояниями рынков и боевыми доктринами. До записи показываются `add`, `update`, `skip` и `conflict`; конфликт по умолчанию оставляет установленную запись и требует явного выбора входящей версии.

Формат описан в `docs/content-pack-format.md`. Минимальный пример находится в `examples/content-packs/skyhold-companion-example.json`, полный редактируемый торговый шаблон 882 года — в `examples/content-packs/air-islands-trade-network-template.json`, а библиотека материалов и характеров рынков — в `examples/content-packs/air-islands-materials-and-country-markets.json`. Лорный источник и авторские дополнения разделены в `docs/air-islands-trade-lore.md`. Full pack выполняет подтверждаемую чистую установку экономики: владения, складские количества и жители сохраняются, но `replaceResources:true` очищает определения пользовательских ресурсов перед импортом. Перед такой установкой нужен экспорт мира. Наборы доступны прямо в `GM → Content packs`; все записи после импорта остаются редактируемыми и удаляемыми.

## Оборона

Вкладка обороны хранит командира, подготовку ополчения, снаряжение, заметки, звуки исходов боя и оборонные отряды.

Отряд имеет сержанта / первый слот, четырех дополнительных участников, тип, экипировку и заметки.

Defence Rating используется как реальная механическая величина для защиты владения.

## Битва за владение

Массовая битва вынесена в отдельное окно. Она использует данные владения, оборонные отряды, здания, теги войск, подготовку, укрепления, планы сторон, угрозу раунда и масштаб столкновения.

Модуль отслеживает:

- силы защитников и нападающих;
- командование;
- позицию;
- стратегию;
- теги войск;
- брешь;
- прогресс цели;
- потери;
- урон владению;
- журнал раундов.

Раунд проводится в два шага. «Подготовить раунд» сохраняет `pendingRound` с формулой, выпавшими d6, полным random trace, snapshot-signature и preview потерь/повреждений, но не меняет жителей, здания или треки. GM отдельно применяет либо отменяет результат. При применении модуль проверяет неизменность snapshot и воспроизводит тот же trace; stale preview или несовпавший fingerprint отклоняется целиком.

Терминальный исход фиксируется отдельной командой. Она сохраняет ограниченный архив воспроизводимых снимков боя и предлагает сразу начать ремонт повреждённых зданий. Сброс незавершённой сцены также оставляет в архиве запись о прерванном бое. При выборе пострадавших модуль использует семантические функции зданий и явный exposure участников: передовая, укреплённый гарнизон, резерв или гражданское ополчение.

## Calendaria

Модуль умеет читать текущую дату из Calendaria, если интеграция доступна.

Хранятся последняя обработанная дата, текст даты, timestamp и количество прошедших quarter days. Это используется для ходов, производства и отчетов.

## Сценические отметки зданий

Здания можно перетаскивать на сцену как отметки. Отметка связывается со зданием и позволяет быстро открыть карточку объекта.

Иконка и изображение могут синхронизироваться с данными здания.

## Права игроков

Глобально ГМ решает, могут ли игроки открывать окно владений.

Для каждого владения отдельно настраивается, могут ли игроки:

- пользоваться складом;
- редактировать обзор;
- редактировать здания;
- редактировать жителей;
- редактировать оборону;
- редактировать подготовку битвы;
- редактировать особые записи;
- управлять корабельными рейсами.

Права Политики настраиваются отдельно; наличие настройки не означает готовность ещё не реализованных действий игрока. Работа моряка в поселении требует права управления жителями.

Игроки не пишут напрямую в world settings. Клиент игрока отправляет patch-запрос ГМу, а клиент ГМа валидирует действие и применяет его к текущим данным.

Клиент заранее вычисляет единый permission context для активного владения. Если активного ГМа или socket Foundry нет, разрешённые игроку операции временно переходят в режим чтения, а в шапке показывается причина. Подключение или смена authority-GM автоматически обновляет открытые окна. При нескольких активных ГМ коммиты выполняет выбранный authority-GM через общую очередь; остальные ГМ направляют ему запрос.

Patch-запросы классифицируются по типу действия: `overview`, `storage`, `buildings`, `residents`, `defense`, `battle`, `special`. Смешанные запросы отклоняются, кроме разрешенных служебных побочных эффектов, например переназначения жителей при работе со зданиями или обороной.

Каждый generic player patch несёт стабильный `operationId`, `expectedRevision` и старые значения изменяемых полей. При тайм-ауте клиент один раз повторяет ту же операцию и заново выбирает активного authority-GM. GM возвращает единый command result с `ok`, `code`, `message`, `retryable`, `operationId` и `revision`; повторная доставка уже применённого operation id получает прежнее подтверждение без повторной записи и side effects.

После обновления модуля все уже подключенные клиенты должны перезагрузить страницу Foundry. Одновременная работа клиентов разных версий не поддерживается; устаревший socket-маршрут, принимавший от игрока полный снимок данных, удалён.

## Хранилище данных

Основные данные разделены на три world setting:

- `skyholdMeta`;
- `skyholdHoldings`;
- `skyholdCatalog`.

Старый общий setting `skyholdData` сохраняется как rollback snapshot для операций, в которых одновременно меняются обе partitions, а также для первичной гидратации split settings из legacy-данных. Обычная правка одного владения не переписывает этот большой snapshot.

При записи используется commit marker. Модуль сначала помечает запись как начатую, записывает только изменившиеся holdings/catalog partitions, затем помечает meta как завершенную. Marker хранит target и previous hashes. Поэтому прерванная одночастная запись восстанавливается вперёд или назад без legacy snapshot; смешанное состояние двухчастной записи откатывается к coherent `skyholdData`. Если обязательный snapshot невозможно сохранить, двухчастный commit не начинается.

GM-only visibility является политикой интерфейса и доступа внутри модуля, а не криптографической секретностью. Данные хранятся в world settings и могут быть прочитаны технически подготовленным клиентом игрока. Сюжетные секреты, которые действительно нельзя передавать клиентам, не следует хранить в GM-владениях без отдельного серверного хранилища.

## Миграции, нормализация и repair

В модуле разделены три режима работы с данными.

`migration` переводит старую структуру данных в актуальную.

`normalization` безопасно доводит данные до валидного состояния при загрузке и обычной записи. Она не должна уничтожать пользовательские настройки.

`repair` предназначен для ручного жесткого восстановления, когда нужно вернуть объект к ожидаемой механической форме. Этот режим может быть разрушительным для пользовательских отклонений.

Историческая команда `GM → Миграция Лапуты` предназначена для полного сброса экономики из snapshot. Этот переход уже выполнен по сообщению владельца мира; команда не является способом применить следующие здания. Для зданий используется текущее сохранение и отдельный [Preview/Apply v16](docs/morale-v16-implementation.md#применение-пользователем). Принудительная замена удаляет дополнительные шаблоны и заменяет механические значения связанных построек, сохраняя жителей, казну, имущество и состояния. Неоднозначные соответствия и незавершённые циклы с резервами блокируют запись. Обычная загрузка этот перенос не запускает.

## Dev-проверка

Выбирать узкую проверку по области изменения; полный список и правила — в [AGENTS.md](AGENTS.md), команды определены в package.json.

| Область | Команда |
|---|---|
| Структура, данные, экономика, storage, бой, UI | npm run suite:structure / suite:data / suite:economy / suite:storage / suite:combat / suite:ui |
| Foundry 13/14 и ленивые границы | npm run compat:check; npm run lazy:check |
| UI и стили | npm run ui:check; npm run css:check |
| JavaScript | npm run lint |
| Производительность | npm run perf; npm run perf:check; npm run perf:budget |
| Перед выпуском | npm run check; npm run css:check; npm run perf:budget |

Проверки защищают импорты, адаптеры Foundry, шаблоны/контролы, чистые расчёты, normalizers, permissions, revision/idempotency и recovery. Node-проверки не подтверждают живой Foundry UI; сценарии собраны в [smoke matrix](docs/manual-foundry-smoke-matrix.md). Fixtures, observer и датированные замеры — в [performance baseline](docs/performance-baseline.md).

Тяжёлые окна рынка, десятника, боя, Политики, корабля, карты и редакторов подключают JS и owner-CSS при первом открытии; lazy:check защищает стартовый граф.

## API

После загрузки мира доступны:

```js
game.fblSkyhold.open();
game.fblSkyhold.rerender();
game.fblSkyhold.diagnostic();
```

Runtime performance observer выключен по умолчанию. Для одного воспроизводимого сценария:

```js
game.fblSkyhold.performance.start("storage-mouse-smoke", {
  foundry: game.version,
  role: game.user.isGM ? "gm" : "player"
});

// Выполни заранее выбранную последовательность действий.

const profile = game.fblSkyhold.performance.stop();
console.log(profile);
```

Доступны также `snapshot()`, `reset()` и `isEnabled()`. Подробности и baseline находятся в `docs/performance-baseline.md`.

Для макросов и внешних ESM-интеграций поддерживается compatibility entry point `modules/fbl-skyhold/scripts/data.js`. Runtime-код самого модуля импортирует конкретных владельцев напрямую, но публичные re-export этого barrel проверяются dev-check.

Пример транзакции без лишней записи, если нужное владение не найдено:

```js
const { SkyholdData, skipTransaction } = await import("/modules/fbl-skyhold/scripts/data.js");

await SkyholdData.transaction((draft, { skip }) => {
  const holding = draft.holdings.find((row) => row.id === "laputa");
  if (!holding) return skip(null); // эквивалентно return skipTransaction(null)
  holding.overview.publicNotes = "Обновлено макросом";
});
```

Updater изменяет выданный `draft`. Если он возвращает обычное значение, изменения
сохраняются, а значение становится результатом Promise. Возврат `skip(value)` или
`skipTransaction(value)` отменяет запись и возвращает `value`.

## Ограничения

Модуль рассчитан на доверенный стол и авторский мир. Он не претендует на универсальный публичный менеджер поселений для всех кампаний Forbidden Lands.

Живая проверка в Foundry после обновления все равно нужна. Статическая проверка и dev-check ловят синтаксис, циклы и чистую логику, но не все особенности ApplicationV2, хуков, CSS-скоупинга и поведения конкретного мира.

## Разработка и CSS

Карта владельцев и helper-классов — в [styles/README.md](styles/README.md). Новые элементы используют существующие toolbar/action-group/card-header/chip/field/stack/cluster и семантические токены.

`npm run css:audit` показывает диагностику; `npm run css:check` проверяет дубли, владельца цветов, отсутствие !important, лимиты и контраст. Новые стили меняют узкий текущий owner. Правила разработки определяет AGENTS.md.

## Сборка релизного архива

```bash
npm run package
```

Команда сначала запускает dev-check, затем создаёт `dist/fbl-skyhold-<version>.zip`. В ZIP входит корневая папка `fbl-skyhold/` и только файлы из allowlist: `module.json`, `README.md`, `assets/`, `docs/`, `examples/`, `lang/`, `scripts/`, `styles/` и `templates/`. Dev-скрипты, `node_modules`, Git/Codex-файлы и временные файлы в архив не попадают.

После сборки содержимое ZIP автоматически сравнивается с allowlist. Если отсутствует runtime-файл или в архив попал лишний файл, команда завершается ошибкой.
